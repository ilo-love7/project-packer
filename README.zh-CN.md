把用户真实做过的事（课程项目、科研、竞赛、开源、学生工作）包装成**面试可防守**的高强度项目经历。

不是简历美化器，更不是造假助手。核心规则一句话：**夸大的天花板 = 追问三层的防守能力**——措辞可以拉满到事实允许的强度，事实（数字、时间、署名、隶属）一个不能动。

> 由 internship-packer（实习经历包装器）转型而来：不再触碰"实习造假"敏感点，定位为求职表达优化工具，覆盖在校生、应届校招、社招转行等更广人群。旧链接经 GitHub 重定向仍然有效。

## 核心设计

- **硬约束优先**：不虚构可核查的事实（雇主隶属/职务/时间/署名/数字）；每个量化数字必须有证据指针；术语如实升级（复现 ≠ 自研）；主动提醒 AI 协作披露口径
- **包装强度分级**：标准档（稳妥防守）与强化档（措辞拉满 + 逐条防守预案），按面试临近度选用，两档数字完全一致
- **考古模式**：直接扫描用户的工作区/仓库，从数据表和结果文件里取数字（不信口述），每条素材带证据指针和取证方式
- **措辞红绿灯**：绿（直接写）/ 黄（必须带限定词）/ 红（必须砍），交稿前逐条过
- **对抗审计**：背调审核员 + 技术面试官双视角，外加数字逐个回溯和隐私扫描，fail 项未处理不得交稿
- **载体重定位**：提前备好"这段是实习吗 / 为什么你没有实习经历"的进攻性回答，把非实习载体翻译成自驱力证据
- **事实档案**：每个用户一份 facts.md 唯一事实源（数字+口径+证据指针+两档定稿+防守分），输出前强制 diff，多次包装不漂移
- **陪练模式**：agent 扮演面试官逐层追问，三维反馈，答崩的表述降档、问题回写追问树与真题库
- **六项可执行检查 + 一层语义审计**——`check_delivery.py`（交付包结构：节齐全/节序/残留占位符）、`lint_resume.py`（动词/红灯词/黄灯词/日期/数字/关键词）、`check_timeline.py`（总时间轴：倒挂/重叠/空档）、`trace_numbers.py`（每个数字回溯到工作区的 文件:行号）、`scan_privacy.py`（密钥与隐私，输出自带打码）、`check_facts.py`（一份档案 × 多份简历：跨版本冲突、未入档数字、闲置素材），最后由 agent 做语义层（追问树/口径/归属）。存在未处理的 fail 不得交稿。
- **JD 解析**：把 JD 整段粘进来，`parse_jd.py` 拆成分组、按频次排序的关键词表，并直接打印 `--keywords` 参数。高频词是硬要求、单次提及是加分项，这个顺序就是证据映射表的优先级。
- **英文与有实习两个分支**：英文 JD 不是翻译，是另一套写法——过去式动词开头、去冠词、单位不省、拼写统一、每条 120 字符；有实习时纪律从"措辞拉满"翻转成"写得准"——证据更强但验证也更容易，要守 NDA 边界、划清自己负责的那部分、备好四个必问题。
- **多项目取舍**：一页简历的项目经历只有 12-20 行，"写几个、每个几条、谁排第一"是算术问题不是审美问题。三维打分（岗位匹配 + 防守分 + 区分度）把每段经历落进 L1 完整 / L2 精简 / L3 一行 / L4 只进面试；**防守分 = 0 的经历最高只能到 L2**，项目按相关度而非时间倒序排。被砍的素材进档案，不进垃圾桶。
- **防守分评分卡**：每条 bullet 0~3 分（证据强度 + 追问树覆盖），<2 分禁入强化档
- **ATS 适配**：纯文本版规范 + JD 关键词覆盖率，缺词三分类，不堆砌不隐写
- **复盘回写**：真实面试被问到但追问树里没有的问题，回写进树并沉淀真题库，命中率统计驱动下次包装

## 使用

**触发方式**：对 agent 说"帮我包装经历 / 这个项目怎么写进简历 / 没有实习经历怎么面试 / 准备面试话术"。

**三种模式自动分流**（阶段 0 判定）：

| 模式 | 适用 | 流程 |
|---|---|---|
| 快速模式 | 只想把一段经历写成简历条目 | 简版收集 → 条目 → 红灯快查，几分钟出稿 |
| 口述模式 | 直接描述经历 | 八件事一次问完 → 全流程 |
| 考古模式 | 给出仓库/工作区路径 | 扫描代码与数据提取证据 → 全流程 |

**完整产出**（全流程）：简历条目 ×4-6 ｜ STAR 故事 ×3（含追问预判树）｜ 30 秒电梯稿 ｜ 诚实边界卡 ｜ 载体重定位话术 ｜ 证据清单 ｜ 审计报告。英文 JD 自动输出双语简历条目与电梯稿。

## 离线检查

五个检查都不需要 agent，纯标准库，不用 `pip install`。它们分别把五条承诺变成可执行的东西：**措辞防守得住**、**数字是真的**、**没漏隐私**、**多个版本之间对得上**、**时间线站得住**。

### 1. 机械层审计 —— `lint_resume.py`

```bash
# 基础检查：动词黑名单 / 红灯词 / 黄灯词 / 日期格式混用 / bullet 超长
python3 scripts/lint_resume.py resume.md

# 每个数字与事实档案逐一对账 + JD 关键词覆盖率
python3 scripts/lint_resume.py resume.md --facts facts.md --keywords "Python,SQL,A/B 测试"

# 让工具自己去 JD 原文里抽关键词
python3 scripts/lint_resume.py resume.md --facts facts.md --jd jd.txt

# 机器可读，方便接进自己的流程
python3 scripts/lint_resume.py resume.md --facts facts.md --json
```

| 参数 | 作用 |
|---|---|
| `--facts facts.md` | 交付稿里出现但档案里没有的显著数字，逐个报警 |
| `--keywords "a,b,c"` | 输出 JD 关键词覆盖率与缺失清单 |
| `--jd jd.txt` | 从 JD 原文抽词并并入 `--keywords` |
| `--max-width N` | bullet 长度上限（按显示宽度算，默认 150 ≈ 2 行；中文按 2 计） |
| `--min-number N` | 小于 N 且无小数点、无百分号的数字视为顺带数字，跳过比对（默认 10） |
| `--strict` | 把警告也算失败，适合放进 CI |
| `--json` | 输出结构化 JSON 而非文本 |

退出码：`0` 干净 ｜ `1` 仅有警告 ｜ `2` 存在错误。

**R7：黄灯词。** `integrity-audit.md` 一直写着「优化/主导/自动化 必须带限定词」，但「带限定词」是个手感判断。R7 把它拆成三个问题，因为三类词缺的本来就不是同一样东西：效果词（优化/提升/降低/缩短/减少/加速/改善/提高）缺**对照数字**——`X→Y`、`从 N 到 M`、`降至 N` 或任意 `%`；归属词（主导/牵头/独立完成/全权）缺**范围**——人数或模块数，或团队类限定；程度词（自动化）缺**覆盖面**——比例、步骤数或触发频率。

它只给 `WARN`，这是刻意的。红灯词可以判死（「自主研发」无论怎么措辞都是错的），黄灯词不行——「优化思路来自导师评审」是句诚实话，只是恰好含「优化」二字。R7 是在提问，不是在判决。有两种情况它拒绝报：词在引号里（审计表写 `"主导" → fix` 是在记录问题，不是在主张），以及词落在分句末尾（`活动确为副部长牵头` 是在描述谁牵头，不是在说自己）——少了后一条，每份交付包都会在自己的审计节上刷警告。它也只查简历条目不查叙述文字，所以交付包第 3 节的 STAR 口播稿豁免。

有两件事它查不了，文档里明说了：「提出」是否真原创，以及带了范围的「主导」是否真是你的。这两件是证据问题不是用词问题，归追问树管。

`parse_jd.py` 也可以单独跑，用来确认它到底抽了什么、为什么抽：

```bash
python3 scripts/parse_jd.py jd.txt              # 分组报告 + 现成的 --keywords 串
python3 scripts/parse_jd.py jd.txt --keywords-only
```

匹配方式是内置词表（硬技能 / 工具与平台 / 软技能）加一条启发式——含数字、含 `+`/`#`、全大写、驼峰，都算技术词，前面挡一张停用词表，所以 `THE`、`AND` 不会变成关键词。边界说清楚：词表之外的中文术语抽不出来，用 `--extra` 补，**工具不会为了填满而编一个词**。

关于降噪：简历里到处是顺带数字（"排查了 3 小时"），逐个对账会把真正的告警淹掉。所以只有「带小数点 / 带百分号 / 数值达到阈值」的数字才逐一对账，其余只统计成一行提示。

「带小数点」这条本身会误伤三类东西，它们长得像小数但不是数据：章节编号（`## 阶段 3.1`）、标识符里的数字（`p95`、`x86`、`H100`、`Python3.11`）、以及引号里被否决的说法（`不说"性能提升 5.3 倍"`）。实测一份正常交付稿会因此多报 5 条假警告。三类都已排除，判据按**出现位置**而不是按词——所以「阶段 3.4」的编号会被跳过，而同一份稿子里「3.4 万条种子数据」照报。

关于 R4 不查什么：交付包第 3 节的 STAR 段落也是 `- ` 开头的列表项，但那是要念出来的口播稿，不是要排进两行的简历条目。以句号结尾的行按叙述文字跳过，并单独计一行提示。代价写在明处：英文条目若以句号结尾就不会被长度检查，所以英文条目请以分号结尾。

### 2. 数字溯源 —— `trace_numbers.py`

这个 skill 的核心主张是"每个数字都有证据指针"。这个脚本就是那句话的文件扫描版：

```bash
python3 scripts/trace_numbers.py resume.md ../my-project
```

```
[HIT ] 5.9
       results/summary.csv:2  …B0005,5.9…
       docs/debug.md:1  …首跑 33.6%，四轮归因后降到 5.9%。…

[MISS] 174
       工作区里没有找到这个数字 → 补证据，或降级为定性描述/删除
```

`MISS` 才是重点：要么这个数字是凭记忆写的（skill 明令禁止），要么证据在扫描不到的地方。两种都需要人来判断——唯独不能让这个数字就这么交稿。

匹配带边界，`3` 不会命中 `13` 或 `3.5` 里的 3，`5.9` 不会命中 `5.95`。交付稿自身被排除，否则每个数字都会在自己的原文里"命中"一次。显著性判定复用 `lint_resume.py` 的同一套规则，所以两个工具不会互相打架。

### 3. 隐私扫描 —— `scan_privacy.py`

```bash
python3 scripts/scan_privacy.py delivery.md
python3 scripts/scan_privacy.py delivery.md --allow "138\d{8}"   # 放行自己的手机号
```

| 级别 | 抓什么 |
|---|---|
| ERROR | 私钥块、`sk-` / `ghp_` / `AKIA` / `xoxb-` 令牌、URL 里内嵌的账号密码、明文口令赋值 |
| WARN | 身份证号、手机号、内网 IP、含用户名的本机绝对路径 |
| INFO | 邮箱（简历留一个自己的是正常的，确认不是他人的即可） |

**命中内容一律先打码再输出。** 一个把你泄露的 API 密钥完整打到终端、然后被粘进聊天窗口的工具，本身就是新的泄露渠道。打码深度按危险等级分档：密钥只留三位；手机号保留头尾（`138****5678`）；内网 IP 和邮箱完整显示——因为你需要看到"是哪台机器、哪个邮箱"才改得动。

退出码：`0` 干净 ｜ `1` 仅有警告 ｜ `2` 存在错误。

拿它扫这个仓库自身，会报出几条来自测试样本和源码里正则定义的警告。这是预期行为——描述 `/home/<用户名>` 的规则自然会命中它自己的描述。真正要守的不变量是 `ERROR = 0`，仓库里有一条测试就断言了这件事（覆盖全部文件）。

### 4. 档案对账 —— `check_facts.py`

"数字在所有版本里完全一致"这条铁律，在此之前只是文档里的一句话。`lint_resume.py --facts` 是拿一份稿对一份档案，看不见两份简历互相打架。

```bash
python3 scripts/check_facts.py facts.md 简历-后端.md 简历-测试.md
python3 scripts/check_facts.py facts.md "简历-*.md"
```

```
[CONFLICT] 「中位误差 #%，覆盖 # 人」第 1 个数字
           简历-后端.md:L5  5.9
           简历-测试.md:L5  6.4
           → 同一指标跨版本数字不一致，比措辞弱致命得多，先对齐再交稿

[ORPHAN] 简历-测试.md：2 个数字不在档案里
           L7  40  「另做了 #% 的优化」
           → 先入档（数字 + 口径 + 证据指针）再定稿，否则下次包装又会漂

[IDLE] 档案里有 3 个数字没进任何版本（素材闲置）
           61 / 7 / 20
```

两级置信度，分界才是重点：

| 级别 | 怎么判 | 退出码 |
|---|---|---|
| `CONFLICT` | 整行所有数字换成 `#` 后完全相同，但其中一个值不一样——复制粘贴后顺手改了一个数。零误报 | 2 |
| `SUSPECT` | 措辞不同（L1 完整版和 L2 精简版本来就不一样），但数字前后各 6 个字符相同，且跨文件。可能误报，所以只报警告交人确认 | 1 |

两者都覆盖不到的情况：同一指标换了说法、连周围用词都换了。工具只报它确定的部分——把猜出来的当错误报，用户很快就会把它关掉。`IDLE` 刻意只做提示：L4 素材按设计就不该出现在简历里。

### 5. 时间线 —— `check_timeline.py`

"核对总时间轴"是最后一条没有可执行形式的硬约束。`lint_resume.py` 只查日期**格式**是否统一，不看区间之间是什么关系。

```bash
python3 scripts/check_timeline.py resume.md
python3 scripts/check_timeline.py resume.md --today 2026.10 --gap-months 3
```

```
总时间轴
  2022.09 - 2026.06   XX大学 计算机科学与技术（本科）
  2024.05               校级一等奖学金
  2025.03 - 2025.06   XX科技 后端开发实习生（全职）
  2025.05 - 2025.08   YY网络 数据平台实习生（全职）
  2025.09 - 2025.12   校园二手书交易服务（课程项目 · 3 人小组）

[ERROR] REVERSED 区间倒挂：2025.12-2025.09「毕业设计：推荐系统」结束早于开始
[WARN]  OVERLAP 2025.05-2025.06 重叠 2 个月：「XX科技 后端开发实习生（全职）」×「YY网络 数据平台实习生（全职）」 两段都声称占满时间 → 确认是否矛盾
```

**合并出来的那张总时间轴才是真正的交付物**——它就是"核对总时间轴"这句话变成一个命令之后的样子。

噪音控制比覆盖面更重要，这几类刻意不报：

| 不报 | 为什么 |
|---|---|
| 与教育背景重叠 | 一段学历跨四年，任何实习都和它重叠。报出来等于每份学生简历都刷三条黄字 |
| 两段区间完全相同 | 同一学期的两个课程项目本来就该同区间，不是矛盾 |
| 单点日期（奖项、证书） | 不是区间，不可能和别人重叠 |
| 表格行 | 交付包的审计表里到处是日期，解析它只会凭空造出重叠和倒挂 |

重叠只有在**两边都声称占满时间**（全职/实习/在职）时才升级为 WARN，其余标为并行经历。倒挂是唯一的 ERROR，因为它是唯一明确写错的东西。

### 6. 交付包结构 —— `check_delivery.py`

阶段 5 有两句硬要求：**节序不要改**、**占位符必须全部替换**。两句都可机械检查，而在这个脚本之前，没有任何一个工具看过交付包的结构。缺口不是假想的——往一份已完成的交付包里插回 `[日期] [改了什么] [为什么]`，`lint_resume`、`check_timeline`、`scan_privacy` 三个工具全部放行（`ERROR 0 / WARN 0`）。结构问题的后果不是难看，是把内部指令和没填的占位符一起投给招聘方。

```bash
python3 scripts/check_delivery.py 交付包.md
python3 scripts/check_delivery.py 交付包.md --strict
```

| 检查 | 含义 | 级别 |
|---|---|---|
| D1 | 第 1-7 节齐全（第 8 节可选） | `ERROR` |
| D2 | 节号从 1 递增不重复，第 1 节必须是简历段 | `ERROR` |
| D3 | **模板自带**的占位符还留着 | `ERROR` |
| D3 | 自己造的方括号 token（如 `[日期]`） | `WARN` |
| D4 | 6.1 没有逐项记全六项机器检查 | `WARN` |
| D5 | 「怎么用这份模板」那段说明还留着 | `ERROR` |

D3 分两级，理由值得知道：模板自带的占位符（`[项目名]`、`[动词]`、`[YYYY.MM-YYYY.MM]`）不用猜——模板列了一份词表，出现了就是没替换；自己造的只能靠形状猜，所以给 WARN。代价写在明处：一段合法的方括号注释（`[注：本机压测口径]`）会被判成警告，确认一次忽略即可。

D3 刻意不查三类：markdown 链接文字（`[文字](url)`）、列表复选框（`- [ ]` / `- [x]`）、纯数字方括号（`[1]` 脚注、正则片段 `[3-9]`）。它们长得像占位符，但都不是。

D5 的存在理由：模板开头有一段写给写作者看的「怎么用这份模板」。忘了删，招聘方就会读到你的内部流程。

## 开发

```bash
python3 -m unittest discover -s tests -v   # 七个脚本的单元测试
python3 scripts/check_docs.py              # 版本 / 阶段数 / 审计条数 / 章节引用 / 链接 / 用例编号 / 更新日志 / 目录树 / 路径引用

```

`check_docs.py` 的存在理由：这个项目发布的东西全是 Markdown，写错一个数字（清单实际 22 条却写"21 条"）不会有编译错误，只会悄悄误导用户和 agent 自己。检查器把这类漂移变成会失败的退出码——现在共十一项，其中四项是因为它真的抓到了这个仓库自己的错：用例分组跳号、升了版本没写更新日志、新增的 `references/` 文件忘了进 README 目录树、`SKILL.md` 里写了一个不存在的 `references/…` 路径。CI 在 Python 3.9 / 3.11 / 3.13 上跑这三条命令。

## 取舍：一页放不下时

大多数人的难点不是"一段经历怎么写强"，而是有五段经历、页面只放得下两段。[references/multi-project.md](references/multi-project.md) 把这件事当成算术题做：

| 项目数 | 每个能分到的 bullet | 结果 |
|---|---|---|
| 2 个 | 5-6 条 | 甜点区，每段都讲得透 |
| 3 个 | 3-4 条 | 刚好，但必须有一个明显主打 |
| 4 个 | 2-3 条 | 每个都浅，读者记不住任何一个 |
| 5 个以上 | 1-2 条 | 已经变成清单，不是简历 |

每段经历按三个维度各打 0-3 分（岗位匹配 / 防守分 / 区分度），落进四档：**L1** 完整版（4-6 条）｜ **L2** 精简版（2-3 条）｜ **L3** 一行版（进"其他项目"区块）｜ **L4** 只进面试、不上简历。**防守分 = 0 的经历（纯口述、无任何指针）无论其他两项多高，最高只能到 L2。** 排序按与岗位的相关度而不是时间倒序——第一段承担"记忆点"职责。

被砍掉的经历不删除：挪进 `facts.md` 与追问树，等面试官问"你还做过什么"时用。**取舍的是版面，不是素材。**

<summary><b>v2.9.0</b>（2026-10-22）黄灯词有了判定谓词</summary>

七条硬约束里，唯一「有文档没检查」的是第 3 条「术语如实升级」。清点下来它已经完成了三分之二：`R2` 直接判死红灯词（自主研发/显著优于/行业领先/填补空白），`R1` 抓句首的软动词（参与/协助/负责）。真正没人管的是中间那一档——这些词可以用，但不带限定地用就是错的。

`R7` 补这一档，设计比词表更值得说。黄档不是一条规则而是三条，因为三类词缺的本来就不是同一样东西：

| 类别 | 词 | 缺什么 | 什么算满足 |
|---|---|---|---|
| 效果词 | 优化 提升 降低 缩短 减少 加速 改善 提高 | 对照数字 | `X→Y`、`从 N 到 M`、`降至 N`、任意 `%` |

| 程度词 | 自动化 | 覆盖面 | 比例、步骤数、定时·每日·每周·自动触发 |

三个比词表更要紧的取舍：

**只给 `WARN`，绝不给 `ERROR`。** 红灯词怎么措辞都错；黄灯词不是——同样的字可以是句诚实话。「优化思路来自导师评审」不是在主张结果。R7 问的是「数字在哪」，而回答可以是「没有，这句是背景」，这正是 `WARN` 的含义。

**词落在分句末尾就不算主张。** 第一版在 `example-student-work.md` 上报了 `活动确为副部长牵头 → pass`——那行是在说谁牵头，不是在说用户牵头。谓词改成：未加引号，**且**后面接的不是分句终止符。少了这条，每份交付包都会在自己的审计节上刷警告，因为那一节就是按 `"主导"限真实主导：…牵头 → pass` 写的。

**范围与 `R4` 一致。** 只查简历条目，不查叙述文字——交付包第 3 节的 STAR 是要念出来的，「我优化了接口」正是你会说的话。代价一样，现在文档里写了两遍：以句号结尾的条目会同时逃过 R4 和 R7，所以中文条目以「；」结尾，英文条目以「；」或不分号结尾。

<summary><b>v2.7.0</b>（2026-10-22）最后四条承诺也变成可执行检查</summary>

这个项目的卖点是"每条承诺都是一个能跑的检查"。老实数一遍：三条有检查，四条没有——**时间线不矛盾**、**档案是唯一事实源**、**多版本数字一致**、**输出前 diff**。这四条在此之前全靠 agent 记得去做。

`check_facts.py` 一次补上后三条。给它一份档案加任意多份简历，它报三类：`CONFLICT`（同一指标数字不同）、`ORPHAN`（简历里有、档案里没有，该入档）、`IDLE`（档案里有、任何版本都没用，只做提示——L4 素材本来就该留在简历外）。冲突检测分两级，分界才是重点：整行骨架相同、只有一个值变了（复制粘贴后顺手改了一个数）判 `CONFLICT`，零误报、退出码 2；措辞不同但数字前后各 6 个字符相同且跨文件判 `SUSPECT`——L1 完整版和 L2 精简版本措辞本来就不一样，所以只报警告交人确认。它查不出的是同一指标连周围用词都换掉的情况，工具把这条边界写在文档里，而不是猜出来当错误报。

`parse_jd.py` 补的是输入侧。`--keywords` 要用户自己拆逗号串，可真实动作是把 JD 整段粘进来。现在能拆成分组、按频次排序的词表——高频是硬要求、单次提及是加分项，这个顺序就是证据映射表的优先级。匹配靠内置词表加一条启发式（含数字 / 含 `+`、`#` / 全大写 / 驼峰），前面挡一张停用词表，所以 `THE`、`AND` 不会变成关键词。词表之外的中文术语抽不出来，用 `--extra` 补，**工具不会编一个词来填满**。`lint_resume.py --jd` 把两者接起来。

`check_docs.py` 加了四项检查，其中三项是因为它已经抓到了这个仓库自己的错：用例分组跳号（C8）、升了版本没写更新日志（C9）、新增的 `references/` 文件忘了进 README 目录树（C10——它在上线一分钟后就抓到了 `example-delivery.md`）、`SKILL.md` 里写了一个不存在的 `references/…` 路径（C11，原来的链接检查看不到，因为它只跟 Markdown 链接，不跟反引号里的路径）。

`references/example-delivery.md` 补的是最后一块内容缺口：一份七节全部填满的交付包。模板是骨架、三个 example 是片段，"最后交到手上到底长什么样"此前没有答案。

写这份示例时顺手修了一条 lint 误报。R4 把交付包第 3 节的 STAR 段落当成超长 bullet——它们确实是 `- ` 开头的列表项，但那是口播稿，不是两行的简历条目，每个照模板做的人都会收到四条假警告。现在以句号结尾的行按叙述文字跳过，并单独计一行提示。代价写在文档里：英文条目若以句号结尾就逃过长度检查，所以英文条目请以分号结尾。

<summary><b>v2.6.0</b>（2026-10-22）多项目压一页简历的取舍</summary>

这个 skill 一直擅长"把一段经历写强"，但对大多数人真正面对的局面一言不发：五段经历，一页纸，不知道该留哪两段。这份缺口现在由 `references/multi-project.md` 补上。

切入角度刻意不浪漫。一页 A4、10.5pt，正文约 45-52 行，项目经历能分到 12-20 行——换算下来两个项目各 5-6 条，五个项目各 1-2 条。到 1-2 条的时候它已经不是简历，是清单。所以默认答案是 2-3 个；每段经历按三个维度各打 0-3 分（岗位匹配 / 防守分 / 区分度），落进四档：L1 完整版、L2 精简版、L3 一行版（进"其他项目"）、L4 只进面试。两条不可让步：**防守分 = 0 的经历（纯口述、无任何证据指针）无论总分多高，最高只能到 L2**；项目按与岗位的相关度排而不是时间倒序，因为第一段承担记忆点。

最让人犹豫的是 L4，所以文档把话说白了：**被砍掉的是版面，不是素材。** 落选的经历挪进 `facts.md` 与追问树，用来回答"你还做过什么"。此外还写了：一人多岗的多版本管理（一份档案、多份简历、数字全版本一致）、7 条反模式（含"为了塞内容调小字号"）、1 个 / 3 个 / 6 个项目三种局面的完整走法。

同时把 `SKILL.md` frontmatter 的 `description` 从 269 字压到 196 字。skill 列表会截断，而被截掉的恰好是触发词所在的后半段——现在触发短语更靠前，并且把"多项目取舍"列进了支持模式。

<summary><b>v2.5.0</b>（2026-10-22）起稿模板 + 补齐缺失的软件工程示例</summary>

这个 skill 一直在描述三样东西——事实档案、真题库、交付包——然后让你"按规范建立"。可仓库里没有任何东西可抄，这是新用户撞上的第一堵墙。现在 `templates/` 里三份都有，每份开头写明怎么用，而且结构是照着机器检查的形状做的：事实档案的数字表列头正好是 `lint_resume.py --facts` 要读的那几列，交付包的节序是固定的。

`references/example-software.md` 补的是示例集里最大的缺口。原有两个例子一个是有硬数据的科研复现、一个是没有硬数字的学生工作，都不覆盖最常见的那类——**"效果"是自己测出来的工程项目**。它走了一遍 p95 480ms→90ms、覆盖率 61%→84%、CI 7分20秒→2分10秒，然后做了另外两个例子做不到的两件事：把**同一段经历重写三遍**分别投后端 / 测试 / 工程岗（事实相同，重心不同），以及演示小组项目里"这是你自己做的吗"该怎么答——既不夸大也不把自己的贡献说没。

同时修掉一条每个交付包都会踩的 lint 误报：R2 原来只要出现红灯词就报错，连引号里的也算，于是审计表里那句 `"自主研发" → cut` 会把审计报告自己报成错误。现在引号内的命中视为「引用」而非「主张」，单独计一行提示。

<summary><b>v2.4.0</b>（2026-10-22）数字溯源与隐私扫描变成可执行工具</summary>

这个 skill 有三条承诺，其中两条在此之前只靠 agent 记得去做。现在都是文件扫描。

`trace_numbers.py` 拿一份交付稿和一个工作区，对每个数字只回答一个问题：**这个数字从哪来的？** 找到就打印 `HIT` 加文件与行号，找不到就打印 `MISS` 并说明"补证据，或降级为定性描述/删除"。匹配带边界（`3` 不会命中 `13` 或 `3.5` 里的 3），交付稿自身被排除，显著性判定与 linter 复用同一套规则——所以两个工具不会互相打架。

`scan_privacy.py` 抓私钥、`sk-`/`ghp_`/`AKIA`/`xoxb-` 令牌、URL 内嵌凭据、明文口令赋值、身份证号、手机号、内网 IP 和含用户名的绝对路径。**输出前一律打码**——一个把泄露的密钥打到你的终端上的工具，本身就是一个新的泄露渠道，不是修复。打码深度按风险分档：密钥只留三位，手机号保留头尾，内网 IP 完整显示，因为你需要看到是哪台机器才改得动。

两者共用 `scripts/_common.py` 做文件遍历，保证"哪些文件算数"只有一处定义。测试从 61 条涨到 103 条，其中一条专门断言仓库自身的脚本里不含形似密钥的字符串。

</details>
