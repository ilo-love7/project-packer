把用户真实做过的事（课程项目、科研、竞赛、开源、学生工作）包装成**面试可防守**的高强度项目经历。

不是简历美化器，更不是造假助手。核心规则一句话：**夸大的天花板 = 追问三层的防守能力**——措辞可以拉满到事实允许的强度，事实（数字、时间、署名、隶属）一个不能动。

> 由 internship-packer（实习经历包装器）转型而来：不再触碰"实习造假"敏感点，定位为求职表达优化工具，覆盖在校生、应届校招、社招转行等更广人群。旧链接经 GitHub 重定向仍然有效。

## 核心设计

- **硬约束优先**：不虚构可核查的事实（雇主隶属/职务/时间/署名/数字）；每个量化数字必须有证据指针；术语如实升级（复现 ≠ 自研）；主动提醒 AI 协作披露口径
- **包装强度分级**：标准档（稳妥防守）与强化档（措辞拉满 + 逐条防守预案），按面试临近度选用，两档数字完全一致
- **考古模式**：直接扫描用户的工作区/仓库，从数据表和结果文件里取数字（不信口述），每条素材带证据指针和取证方式
- **措辞红绿灯**：绿（直接写）/ 黄（必须带限定词）/ 红（必须砍），交稿前逐条过
- **对抗审计**：背调审核员 + 技术面试官双视角，外加数字逐个回溯和隐私扫描，fail 项未处理不得交稿
- **载体重定位**：提前备好"这段是实习吗 / 为什么你没有实习经历"的进攻性回答，把非实习载体翻译成自驱力证据
- **事实档案**：每个用户一份 facts.md 唯一事实源（数字+口径+证据指针+两档定稿+防守分），输出前强制 diff，多次包装不漂移
- **陪练模式**：agent 扮演面试官逐层追问，三维反馈，答崩的表述降档、问题回写追问树与真题库
- **四层审计**：三层可执行检查 + 一层语义审计——`lint_resume.py`（动词/红灯词/日期/数字/关键词）、`trace_numbers.py`（每个数字回溯到工作区的 文件:行号）、`scan_privacy.py`（密钥与隐私，输出自带打码），最后由 agent 做语义层（追问树/口径/归属）。存在未处理的 fail 不得交稿。
- **多项目取舍**：一页简历的项目经历只有 12-20 行，"写几个、每个几条、谁排第一"是算术问题不是审美问题。三维打分（岗位匹配 + 防守分 + 区分度）把每段经历落进 L1 完整 / L2 精简 / L3 一行 / L4 只进面试；**防守分 = 0 的经历最高只能到 L2**，项目按相关度而非时间倒序排。被砍的素材进档案，不进垃圾桶。
- **防守分评分卡**：每条 bullet 0~3 分（证据强度 + 追问树覆盖），<2 分禁入强化档
- **ATS 适配**：纯文本版规范 + JD 关键词覆盖率，缺词三分类，不堆砌不隐写
- **复盘回写**：真实面试被问到但追问树里没有的问题，回写进树并沉淀真题库，命中率统计驱动下次包装

## 使用

**触发方式**：对 agent 说"帮我包装经历 / 这个项目怎么写进简历 / 没有实习经历怎么面试 / 准备面试话术"。

**三种模式自动分流**（阶段 0 判定）：

| 模式 | 适用 | 流程 |
|---|---|---|
| 快速模式 | 只想把一段经历写成简历条目 | 简版收集 → 条目 → 红灯快查，几分钟出稿 |
| 口述模式 | 直接描述经历 | 八件事一次问完 → 全流程 |
| 考古模式 | 给出仓库/工作区路径 | 扫描代码与数据提取证据 → 全流程 |

**完整产出**（全流程）：简历条目 ×4-6 ｜ STAR 故事 ×3（含追问预判树）｜ 30 秒电梯稿 ｜ 诚实边界卡 ｜ 载体重定位话术 ｜ 证据清单 ｜ 审计报告。英文 JD 自动输出双语简历条目与电梯稿。

## 离线检查

三个检查都不需要 agent，纯标准库，不用 `pip install`。它们分别把三条承诺变成可执行的东西：**措辞防守得住**、**数字是真的**、**没漏隐私**。

### 1. 机械层审计 —— `lint_resume.py`

```bash
# 基础检查：动词黑名单 / 红灯词 / 日期格式混用 / bullet 超长
python3 scripts/lint_resume.py resume.md

# 每个数字与事实档案逐一对账 + JD 关键词覆盖率
python3 scripts/lint_resume.py resume.md --facts facts.md --keywords "Python,SQL,A/B 测试"

# 机器可读，方便接进自己的流程
python3 scripts/lint_resume.py resume.md --facts facts.md --json
```

| 参数 | 作用 |
|---|---|
| `--facts facts.md` | 交付稿里出现但档案里没有的显著数字，逐个报警 |
| `--keywords "a,b,c"` | 输出 JD 关键词覆盖率与缺失清单 |
| `--max-width N` | bullet 长度上限（按显示宽度算，默认 150 ≈ 2 行；中文按 2 计） |
| `--min-number N` | 小于 N 且无小数点、无百分号的数字视为顺带数字，跳过比对（默认 10） |
| `--strict` | 把警告也算失败，适合放进 CI |
| `--json` | 输出结构化 JSON 而非文本 |

退出码：`0` 干净 ｜ `1` 仅有警告 ｜ `2` 存在错误。

关于降噪：简历里到处是顺带数字（"排查了 3 小时"），逐个对账会把真正的告警淹掉。所以只有「带小数点 / 带百分号 / 数值达到阈值」的数字才逐一对账，其余只统计成一行提示。

### 2. 数字溯源 —— `trace_numbers.py`

这个 skill 的核心主张是"每个数字都有证据指针"。这个脚本就是那句话的文件扫描版：

```bash
python3 scripts/trace_numbers.py resume.md ../my-project
```

```
[HIT ] 5.9
       results/summary.csv:2  …B0005,5.9…
       docs/debug.md:1  …首跑 33.6%，四轮归因后降到 5.9%。…

[MISS] 174
       工作区里没有找到这个数字 → 补证据，或降级为定性描述/删除
```

`MISS` 才是重点：要么这个数字是凭记忆写的（skill 明令禁止），要么证据在扫描不到的地方。两种都需要人来判断——唯独不能让这个数字就这么交稿。

匹配带边界，`3` 不会命中 `13` 或 `3.5` 里的 3，`5.9` 不会命中 `5.95`。交付稿自身被排除，否则每个数字都会在自己的原文里"命中"一次。显著性判定复用 `lint_resume.py` 的同一套规则，所以两个工具不会互相打架。

### 3. 隐私扫描 —— `scan_privacy.py`

```bash
python3 scripts/scan_privacy.py delivery.md
python3 scripts/scan_privacy.py delivery.md --allow "138\d{8}"   # 放行自己的手机号
```

| 级别 | 抓什么 |
|---|---|
| ERROR | 私钥块、`sk-` / `ghp_` / `AKIA` / `xoxb-` 令牌、URL 里内嵌的账号密码、明文口令赋值 |
| WARN | 身份证号、手机号、内网 IP、含用户名的本机绝对路径 |
| INFO | 邮箱（简历留一个自己的是正常的，确认不是他人的即可） |

**命中内容一律先打码再输出。** 一个把你泄露的 API 密钥完整打到终端、然后被粘进聊天窗口的工具，本身就是新的泄露渠道。打码深度按危险等级分档：密钥只留三位；手机号保留头尾（`138****5678`）；内网 IP 和邮箱完整显示——因为你需要看到"是哪台机器、哪个邮箱"才改得动。

退出码：`0` 干净 ｜ `1` 仅有警告 ｜ `2` 存在错误。

拿它扫这个仓库自身，会报出几条来自测试样本和源码里正则定义的警告。这是预期行为——描述 `/home/<用户名>` 的规则自然会命中它自己的描述。真正要守的不变量是 `ERROR = 0`，仓库里有一条测试就断言了这件事（覆盖全部文件）。

## 开发

```bash
python3 -m unittest discover -s tests -v   # 四个脚本的单元测试
python3 scripts/check_docs.py              # 版本徽章 / 阶段数 / 审计条数 / 章节引用 / 相对链接
python3 scripts/lint_resume.py references/example-battery.md --strict
```

`check_docs.py` 的存在理由：这个项目发布的东西全是 Markdown，写错一个数字（清单实际 22 条却写"21 条"）不会有编译错误，只会悄悄误导用户和 agent 自己。检查器把这类漂移变成会失败的退出码。CI 在 Python 3.9 / 3.11 / 3.13 上跑这三条命令。

- [example-software.md](references/example-software.md)：三人小组课程项目后端 → p95 480ms→90ms、覆盖率 61%→84%、CI 7分20秒→2分10秒；展示同一段经历按研发/测试/工程三种岗换弹头的写法，以及小组项目里"这是你自己做的吗"的标准答法

## 取舍：一页放不下时

大多数人的难点不是"一段经历怎么写强"，而是有五段经历、页面只放得下两段。[references/multi-project.md](references/multi-project.md) 把这件事当成算术题做：

| 项目数 | 每个能分到的 bullet | 结果 |
|---|---|---|
| 2 个 | 5-6 条 | 甜点区，每段都讲得透 |
| 3 个 | 3-4 条 | 刚好，但必须有一个明显主打 |
| 4 个 | 2-3 条 | 每个都浅，读者记不住任何一个 |
| 5 个以上 | 1-2 条 | 已经变成清单，不是简历 |

每段经历按三个维度各打 0-3 分（岗位匹配 / 防守分 / 区分度），落进四档：**L1** 完整版（4-6 条）｜ **L2** 精简版（2-3 条）｜ **L3** 一行版（进"其他项目"区块）｜ **L4** 只进面试、不上简历。**防守分 = 0 的经历（纯口述、无任何指针）无论其他两项多高，最高只能到 L2。** 排序按与岗位的相关度而不是时间倒序——第一段承担"记忆点"职责。

被砍掉的经历不删除：挪进 `facts.md` 与追问树，等面试官问"你还做过什么"时用。**取舍的是版面，不是素材。**

## 从这里开始

这三个模板存在的唯一目的，是让第一次跑不用面对空白页：

| 文件 | 什么时候用 |
|---|---|
| [templates/facts.template.md](templates/facts.template.md) | 包装任何东西之前，复制成 `facts.md`。里面「数字清单」的表头（数字/口径/证据指针/取证方式/防守分）就是后面机器检查的对齐基准 |
| [templates/delivery.template.md](templates/delivery.template.md) | 阶段 5 交付时复制。节序是固定的：简历段放最前，因为用户 80% 的时间只看前两屏 |
| [templates/question-bank.template.md](templates/question-bank.template.md) | 面完第一场就复制。一条真实问题 = 一条记录，标 ✅ 命中 / 🟡 树外答上 / ❌ 答崩 |

<summary><b>v2.6.0</b>（2026-10-22）多项目压一页简历的取舍</summary>

这个 skill 一直擅长"把一段经历写强"，但对大多数人真正面对的局面一言不发：五段经历，一页纸，不知道该留哪两段。这份缺口现在由 `references/multi-project.md` 补上。

切入角度刻意不浪漫。一页 A4、10.5pt，正文约 45-52 行，项目经历能分到 12-20 行——换算下来两个项目各 5-6 条，五个项目各 1-2 条。到 1-2 条的时候它已经不是简历，是清单。所以默认答案是 2-3 个；每段经历按三个维度各打 0-3 分（岗位匹配 / 防守分 / 区分度），落进四档：L1 完整版、L2 精简版、L3 一行版（进"其他项目"）、L4 只进面试。两条不可让步：**防守分 = 0 的经历（纯口述、无任何证据指针）无论总分多高，最高只能到 L2**；项目按与岗位的相关度排而不是时间倒序，因为第一段承担记忆点。

最让人犹豫的是 L4，所以文档把话说白了：**被砍掉的是版面，不是素材。** 落选的经历挪进 `facts.md` 与追问树，用来回答"你还做过什么"。此外还写了：一人多岗的多版本管理（一份档案、多份简历、数字全版本一致）、7 条反模式（含"为了塞内容调小字号"）、1 个 / 3 个 / 6 个项目三种局面的完整走法。

同时把 `SKILL.md` frontmatter 的 `description` 从 269 字压到 196 字。skill 列表会截断，而被截掉的恰好是触发词所在的后半段——现在触发短语更靠前，并且把"多项目取舍"列进了支持模式。

这个 skill 一直在描述三样东西——事实档案、真题库、交付包——然后让你"按规范建立"。可仓库里没有任何东西可抄，这是新用户撞上的第一堵墙。现在 `templates/` 里三份都有，每份开头写明怎么用，而且结构是照着机器检查的形状做的：事实档案的数字表列头正好是 `lint_resume.py --facts` 要读的那几列，交付包的节序是固定的。

<details>
<summary><b>v2.4.0</b>（2026-10-22）数字溯源与隐私扫描变成可执行工具</summary>

这个 skill 有三条承诺，其中两条在此之前只靠 agent 记得去做。现在都是文件扫描。

`trace_numbers.py` 拿一份交付稿和一个工作区，对每个数字只回答一个问题：**这个数字从哪来的？** 找到就打印 `HIT` 加文件与行号，找不到就打印 `MISS` 并说明"补证据，或降级为定性描述/删除"。匹配带边界（`3` 不会命中 `13` 或 `3.5` 里的 3），交付稿自身被排除，显著性判定与 linter 复用同一套规则——所以两个工具不会互相打架。

`scan_privacy.py` 抓私钥、`sk-`/`ghp_`/`AKIA`/`xoxb-` 令牌、URL 内嵌凭据、明文口令赋值、身份证号、手机号、内网 IP 和含用户名的绝对路径。**输出前一律打码**——一个把泄露的密钥打到你的终端上的工具，本身就是一个新的泄露渠道，不是修复。打码深度按风险分档：密钥只留三位，手机号保留头尾，内网 IP 完整显示，因为你需要看到是哪台机器才改得动。

两者共用 `scripts/_common.py` 做文件遍历，保证"哪些文件算数"只有一处定义。测试从 61 条涨到 103 条，其中一条专门断言仓库自身的脚本里不含形似密钥的字符串。
