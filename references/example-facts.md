## 校园二手书交易服务

- **时间**：2025.09 - 2025.12
- **载体**：课程项目（3 人小组）
- **角色**：参与执行 —— 负责后端接口与测试，CI 归我，架构选型是组长定的
- **一句事实**：把校园二手书交易做成可用的 Web 服务，交付 12 个 REST 接口；重写查询链路后 p95 从 480ms 降到 90ms，测试覆盖率从 61% 提到 84%
- **目标岗位**：后端开发 / 测试开发（同一段经历投两个岗，弹头不同，数字不动）

### 数字清单

| 数字 | 口径（中位/均值、样本量、划分方式） | 证据指针 | 取证方式 | 防守分 |
|---|---|---|---|---|
| 12 个 | REST 接口数量，含鉴权与搜索 | `app/api/routes.py` | 数 `@router` 装饰器个数 | 2 |
| 480ms → 90ms | p95 延迟；本机 locust 200 并发，非生产环境 | `bench/before.txt`、`bench/after.txt` | 两个文件各读 `p95` 行 | 2 |
| 410ms | 480ms 中落在 DB 段的耗时，分段打点 | `bench/before.txt` | 读 `db_segment` 行 | 2 |
| 21 条 | 同一搜索请求发出的重复 SQL 数 | `logs/slow_2026-10-08.log` | 数同一 trace id 下的 SELECT | 2 |
| 94% | Redis 缓存命中率（排除假设用） | `logs/cache_2026-10-08.log` | 读 `hit_rate` 汇总行 | 1 |
| 47 个 | pytest 用例数 | `tests/` | `pytest --collect-only -q \| wc -l` | 2 |
| 61% → 84% | **行**覆盖率（不是分支覆盖率） | `coverage.xml` | 读 `line-rate` 属性 | 2 |
| 7 分 20 秒 → 2 分 10 秒 | GitHub Actions 单次全流程时长 | Actions 两次 run 的 Duration 列 | 打开 run 页面读 Duration | 2 |


### 边界卡摘要

- 不说"生产环境 p95 90ms"：本机压测，200 并发，无真实网络与数据分布 → "本机压测口径，200 并发，非生产环境"
- 不说"支撑 3.4 万用户"：那是种子数据行数 → "3.4 万条种子数据"
- 不说"覆盖率 84%"就完事：那是行覆盖率，分支只有 68% → 主动说明口径
- 不说"性能提升 5.3 倍"：480/90 ≈ 5.3 是**延迟比**不是吞吐比 → "p95 延迟从 480ms 降到 90ms"
- 归属如实：接口与测试是我做的，CI 是我做的，架构选型是组长定的 → 被问"这是你主导的吗"时按这条答

## 这份示例想说明的四件事

1. **数字清单的"口径"列比"数字"列更重要。** 84% 是行覆盖率、18/18 的分母是观测数、
   3.4 万条是种子数据——这三处一旦混用，追问第二层就崩，而数字本身一个都没错。
2. **防守分 0 的行不该存在。** 上面两张表最低是 1（有指针但没实际验证）。
   如果某行你只能写 0（仅口述），那它就不该出现在简历上，最多进面试垫话。
3. **两档措辞都存档。** 标准档和强化档的数字必须逐字一致；`check_facts.py` 会把
   它们当两个版本来对账，CONFLICT 一出现就说明哪里漂了。
4. **边界卡是档案的一部分，不是交付包的附属品。** 它记录的是"哪些话不能说满"，
   下次包装同一段经历时直接取用，不用重新想一遍。
