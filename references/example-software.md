# 软件工程示例：课程项目后端 → 简历与面试稿

真实度注记：本例基于常见的三人小组课程项目构造，用于展示**软件工程类指标**（延迟、覆盖率、CI 时长）的包装形态，以及**同一段经历的三种换弹头**。具体数值仅为示意格式，实际使用时每个数字都必须能在你的仓库里定位到。

它与另外两个示例的分工：`example-battery.md` 是有硬数据的科研复现，`example-student-work.md` 是完全没有硬数字的学生工作。本例补的是最常见的那一类——**代码写得出来、但"效果"全靠自己测的工程项目**。

---

## 阶段 0-1：素材清单（考古模式）

| 素材（一句事实） | 证据指针 | 取证方式 |
|---|---|---|
| 课程项目「校园二手书交易服务」，3 人小组，我负责后端 | `README.md` 的 Contributors 段 | 直接读 |
| 12 个 REST 接口（图书 CRUD、订单、搜索） | `app/routes/` 目录 | 数路由注册数 |
| 压测 p95 从 480ms 降到 90ms | `bench/before.txt`、`bench/after.txt` | 两个文件里的 `p95` 行 |
| 定位并消除 N+1 查询，补 3 个复合索引 | commit `a1f3c9d`、`d4e7b21` | `git show --stat` |
| 种子数据 3.4 万条 | `scripts/seed.py` 的运行日志 | 日志最后一行计数 |
| 测试覆盖率 61% → 84% | `.coverage` 报告、CI 日志 | `pytest --cov` 输出的 TOTAL 行 |
| CI 从 7 分 20 秒降到 2 分 10 秒 | GitHub Actions 两次 run 的时长 | Actions 页面 Duration 列 |

**注意这组数字的口径**——它们是这类项目最容易吹过头的地方：

- p95 是**本机 locust 压测**，不是生产环境，没有真实并发；
- 3.4 万条是**种子数据**，不是用户量；
- 覆盖率 84% 是**行覆盖率**，不是分支覆盖率。

三个数字都真实，但三个口径都必须写清楚。不写口径 = 给面试官留了追问三层的入口。

## 阶段 2：岗位对齐（换弹头的依据）

同一个项目，投不同岗位时重心完全不同（规则见 `references/templates.md` 第 5 节「按岗位换弹头」）：

| 岗位类型 | 强调什么 | 本例里对应的素材 |
|---|---|---|
| 研发/后端 | 数据模型设计、索引与查询优化、接口契约 | N+1 与索引那一段 |
| 测试/质量 | 覆盖率提升、防回归断言、压测方法 | 覆盖率 61%→84%、bench 脚本 |
| 工程/平台 | CI 提速、依赖缓存、可复现构建 | 7 分 20 秒→2 分 10 秒 |

**同一段经历，三份简历不该写成一样的。** 下面给出三版。

## 阶段 3.1：简历条目（三个版本）

### 版本 A：后端研发岗

```text
校园二手书交易服务（课程项目 · 3 人小组，负责后端）      2025.09-2025.12
· 实现 12 个 REST 接口（图书 CRUD / 订单 / 搜索），PostgreSQL +
  Redis 缓存，服务 3.4 万条种子数据；
· 通过分段计时与慢查询日志定位 N+1 查询，补 3 个复合索引，本机
  压测 p95 从 480ms 降至 90ms（locust，非生产环境）；
· 用 pytest 补 47 个用例把行覆盖率从 61% 提到 84%，关键路径加
  防回归断言。
```

### 版本 B：测试 / 质量岗

```text
校园二手书交易服务（课程项目 · 3 人小组，负责后端与测试）  2025.09-2025.12
· 为 12 个 REST 接口建立 pytest 用例集（47 个用例），行覆盖率
  从 61% 提到 84%，订单状态机覆盖全部 5 条迁移路径；
· 用 locust 搭建可复跑的压测脚本，把 p95 从 480ms 压到 90ms，
  压测脚本与基线数据入库供回归对比；
· 在关键路径加防回归断言，拦截过 2 次缓存键拼写错误导致的错读。
```

### 版本 C：工程 / 平台岗

```text
校园二手书交易服务（课程项目 · 3 人小组，负责后端与 CI）    2025.09-2025.12
· 重构 GitHub Actions 流水线：拆 lint / test / bench 三个 job，
  加依赖缓存，CI 时长从 7 分 20 秒降到 2 分 10 秒；
· 把种子数据生成与压测脚本做成一条命令可复现，新组员 10 分钟内
  能跑起完整环境；
· 实现 12 个 REST 接口并补 pytest 用例集，行覆盖率 61% → 84%。
```

三版的事实完全相同：同样的 12 个接口、同样的 480→90、同样的 61→84。**换的只是顺序和重心**，不是数字。

## 阶段 3.2：STAR 故事（p95 480ms → 90ms）

【S】课程项目中期演示时，图书搜索接口点一下要等半秒多，演示现场很尴尬。小组 3 人，我负责后端。

【T】要在两周内把响应时间压下来，且不能靠加机器（课程项目没有预算）。

【A】三步：
1. **先量再改**——在接口里分段打点（路由 → 业务 → DB → 序列化），发现 480ms 里有 410ms 在 DB；
2. **排除假设**——先怀疑是 Redis 没命中，加了命中率日志，命中率 94%，排除；再看慢查询日志，同一个搜索请求打了 21 条几乎一样的 SQL，是典型的 N+1；
3. **定位根因**——ORM 的懒加载在序列化时才触发，循环里每本书都去查一次作者表；
   改成一次性 `JOIN` 预加载，再对 `(category, created_at)` 补复合索引，
   `EXPLAIN` 确认从 `Seq Scan` 变成 `Index Scan`。

【R】p95 480ms → 90ms（本机 locust，200 并发，非生产环境）；压测脚本和前后基线数据提交进仓库，后续改动可以直接对比。

【追问预判树】

- **1 层：怎么确定是数据库的问题，而不是网络或序列化？**
  → 分段计时打点，四段耗时占比 410/480 在 DB 段；先排除缓存（命中率日志 94%）再进 SQL。证据：`bench/before.txt` 的分段耗时。

- **2 层：为什么加索引就能从 480 降到 90？原理是什么？**
  → 原查询对 `category` 单列无索引，走全表扫描（3.4 万行），且每行要回表取 `created_at`；复合索引 `(category, created_at)` 让过滤和排序在同一棵 B+ 树上完成，回表次数从 3.4 万降到命中行数。`EXPLAIN` 前后对比：`Seq Scan` → `Index Scan`。

- **3 层：这是你自己做的吗？**
  → 分层讲：分段打点和索引是我做的；N+1 是组员 code review 时先看出来的，我负责验证和改法；索引字段的选择是三个人一起对着查询模式定的。压测脚本是另一个组员写的，我只跑了它。

第 3 层的答法值得注意：**没有把组员的贡献说成自己的，也没有因此把自己的贡献说没**。面试官问这句往往不是查岗，是看你分不分得清。

## 阶段 3.3：诚实边界卡

- **不说"生产环境 p95 90ms"**：那是本机压测，200 并发，没有真实网络和真实数据分布 → "本机压测口径，200 并发，非生产环境"；
- **不说"支撑 3.4 万用户"**：3.4 万是种子数据行数，不是用户量，也没有并发用户 → "3.4 万条种子数据"；
- **不说"性能提升 5.3 倍"**：480/90 ≈ 5.3 是**延迟比**，不是吞吐比，我并没有测吞吐 → "p95 延迟从 480ms 降到 90ms"；
- **不说"覆盖率 84%"就完事**：那是行覆盖率，分支覆盖率只有 68% → 主动说明是行覆盖率。

四条边界卡的共同点：**数字都是真的，但口径都可能被听成更大的那个**。边界卡的作用就是提前把口径说死。

## 阶段 3.4：载体重定位话术

```text
【被问"这是课程项目吧，跟真实业务差很远？"】
"是课程项目，但我是按真实服务的标准要求自己的：有压测基线、有覆盖率门槛、
有 CI 门禁。比如 p95 那个优化，我不是调参数调出来的，是先分段打点定位到
DB 段，再用慢查询日志找到 N+1，最后用 EXPLAIN 确认索引生效——这套方法在
真实业务里是一样的，差别只是数据量和并发量级。"
```

要点：**不否认载体，也不为它道歉**，直接把"课程项目"翻译成"用工程标准自我要求"。承认差别（数据量、并发量级），但不接受"方法不一样"这个暗示。

## 阶段 4：审计结论（本例特有）

| 初稿写法 | 结论 | 理由与改法 |
|---|---|---|
| "独立完成了整个后端" | **cut** | 3 人小组，组员写了压测脚本并发现了 N+1 → 改为"负责后端" |
| "显著提升了系统性能" | **fix** | "显著"是黄灯词且无数字 → 改为"p95 从 480ms 降至 90ms" |
| "QPS 提升 5 倍" | **cut** | 只测了延迟，没测吞吐，5 倍是拿延迟比冒充吞吐比 → 删 |
| "支撑 3.4 万用户" | **fix** | 3.4 万是数据行数不是用户数 → 改为"3.4 万条种子数据" |
| "自主研发了搜索服务" | **cut** | 复现课程给的骨架 + 自己改，不构成自研 → 改为"实现" |
| "p95 从 480ms 降至 90ms" | **pass** | 有 `bench/before.txt` 与 `bench/after.txt`，口径已注明本机压测 |

最后一条能 pass，不是因为数字好看，是因为**证据和口径都在**。前五条被改，也不是因为措辞不好看，是因为**措辞比事实大了一圈**。

---

## 这个例子想说明的三件事

1. **软件项目的"效果"是自己测的**，所以口径比数字更重要。480→90 是真的，但"非生产环境、200 并发"这半句才是它能不能被防守的关键。
2. **同一段经历可以有三个重心**（研发 / 测试 / 工程），但三版的事实必须完全一致。数字对不上比措辞弱致命得多。
3. **归属问题在小组项目里是必问题**。第 3 层追问的标准答法不是"都是我自己做的"，而是"哪部分是我做的、哪部分是别人的、我怎么验证的"。
